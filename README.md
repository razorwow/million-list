# Список из 1 000 000 элементов - тестовое задание (Fullstack)

Приложение для работы со списком элементов с ID от 1 до 1 000 000: выбор, фильтрация,
изменение порядка выбранных через Drag & Drop. Состояние выбора и порядок хранятся
на сервере в оперативной памяти; база данных и авторизация не используются.

**Стек:** Express.js (backend) + React + Vite + TypeScript (frontend).
В продакшене один процесс Express раздаёт и API, и собранный фронтенд.

**Демо:** <https://million-list-1qn5.onrender.com/>
**Исходный код:** <https://github.com/razorwow/million-list>

## 1. Как запустить локально

Нужен Node.js 18+. Подойдёт npm (идёт в комплекте с Node) или pnpm.

### Вариант A - как в продакшене (один процесс, порт 4000)

```bash
npm run setup     # зависимости backend и frontend
npm run build     # сборка frontend в frontend/dist
npm start         # Express на http://localhost:4000 (API + UI)
```

Открыть <http://localhost:4000>.

### Вариант B - режим разработки (два процесса, HMR)

```bash
npm run dev:backend    # Express на :4000
npm run dev:frontend   # Vite на :5173, /api проксируется на :4000
```

Открыть <http://localhost:5173>.

### Тесты

```bash
npm test
```

Два набора:
* `backend/scripts/smoke.mjs` - 26 проверок логики: фильтр сверяется с полным перебором
  всех 1 000 000 чисел, пагинация, добавление, порядок, дедупликация, батчинг,
  гарантия отсутствия повторного добавления;
* `backend/scripts/http-test.mjs` - 25 проверок HTTP API на реальном Express-приложении.

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `4000` | порт сервера |
| `BATCH_NORMAL_MS` | `1000` | окно батчинга получения и изменения данных |
| `BATCH_ADD_MS` | `10000` | окно батчинга добавления элементов |
| `BATCH_GRACE_MS` | `30` | короткое окно для первой операции после простоя |

## 2. Соответствие требованиям

| Требование | Реализация |
|---|---|
| Два контейнера: слева все, кроме выбранных; справа выбранные | `frontend/src/components/LeftPane.tsx`, `RightPane.tsx` |
| Фильтрация элементов по ID (левый контейнер) | `backend/src/store.js` → `listLeft`, подстрочный фильтр `backend/src/filter.js` |
| Бесконечная прокрутка, первая загрузка ≤ 20 | `frontend/src/hooks/useInfiniteScroll.ts` + `useInfiniteList.ts`; сервер жёстко ограничивает `limit` двадцатью |

| Добавление нового элемента: ID вручную, произвольный, без дублей | `POST /api/items` → `store.addItem`; нормализация и проверка существования |
| Фильтрация выбранных по ID | `store.listRight` |
| Изменение порядка Drag & Drop | `RightPane.tsx` (нативный HTML5 DnD) + `POST /api/reorder` |
| Drag & Drop при активном фильтре | Перестановка по ID и ориентиру (`anchorId` + `before/after`), а не по индексу - скрытые фильтром элементы не мешают |
| Бесконечная прокрутка в правом контейнере | тот же hook в `RightPane.tsx` |
| Сохранение выбранных и их порядка после перезагрузки | Сервер - источник истины; при старте фронтенд читает `GET /api/right` |
| Значения фильтров НЕ сохраняются | Фильтр живёт только в состоянии React (`useState`), никуда не пишется |
| Хранение на сервере в оперативной памяти, общее для всех | `backend/src/store.js`, без БД и авторизации |
| Очередь обработки запросов | `backend/src/queue.js` - лейны `normal` и `add` |
| Дедупликация запросов | Ключ операции (`left|<filter>|<offset>`, `add|<id>`, …); одинаковые запросы в одном окне склеиваются |
| Техническая гарантия отсутствия повторного добавления | Батч применяется синхронно и последовательно, проверка существования и вставка не могут разъехаться (проверено тестом на 200 параллельных запросов) |
| Батчинг добавления - раз в 10 секунд | Лейн `add`, `BATCH_ADD_MS = 10000` |
| Батчинг получения и изменения - раз в секунду | Лейн `normal`, `BATCH_NORMAL_MS = 1000` |

## 3. Backend: как устроено

### Модель данных

Один миллион элементов **не материализуется** в памяти. Базовый диапазон `1..1 000 000`
существует виртуально, а хранятся только изменяемые части:

```
selected    - упорядоченный массив выбранных ID (порядок задаёт пользователь)
selectedSet - тот же набор для проверки вхождения за O(1)
customIds   - ID, добавленные пользователем вручную вне базового диапазона
```

Память под состояние не зависит от размера базового диапазона.

Нормализация ID: пробелы обрезаются; числовые значения канонизируются (`042` → `42`),
поэтому `042` и `42` - один и тот же ID. Нечисловые строки (`user-777`) допустимы.
ID из диапазона `1..1 000 000` считается уже существующим, и добавить его повторно нельзя.

### Фильтр по подстроке

Наивный перебор миллиона чисел на каждый запрос не нужен. Число содержит подстроку `sub`
тогда и только тогда, когда `sub` стоит в нём на некоторой позиции, поэтому совпадения
перечисляются как `prefix + sub + suffix` по всем длинам числа и позициям вставки
(`backend/src/filter.js`). Результат сортируется и кешируется по строке фильтра, а батчинг
и дедупликация гарантируют, что дорогое вычисление выполняется один раз на уникальный фильтр.

Корректность алгоритма проверяется сравнением с полным перебором всех 1 000 000 чисел -
в том числе для каверзных подстрок `0`, `007`, `0000`, `1000000`.

### Очередь, дедупликация, батчинг

Все операции чтения и изменения проходят через очередь (`backend/src/queue.js`):

* **лейн `normal`** - получение и изменение данных (списки, `select`, `deselect`, `reorder`),
  флеш не чаще одного раза в секунду;
* **лейн `add`** - добавление элементов, флеш не чаще одного раза в 10 секунд.

Дедупликация: операции с одинаковым ключом, попавшие в одно окно, выполняются один раз,
а все ожидающие запросы получают общий результат. Это гасит дубли от повторных запросов,
ретраев и двойных вызовов.

Первая операция после простоя обрабатывается через короткое окно `BATCH_GRACE_MS`, чтобы
успеть собрать дубли из одной пачки; дальше флеши идут не чаще заданного интервала.

Замеры на живом сервере (два последовательных запроса):

| Операция | Первый запрос (лейн простаивал) | Второй запрос (в окне) |
|---|---|---|
| `GET /api/left` | ~117 мс | **1004 мс** |
| `POST /api/items` | ~84 мс | **10002 мс** |

В интерфейсе есть строка диагностики: окна батчинга, число флешей, сколько запросов склеено
и сколько операций ждёт в очереди (`GET /api/stats`).

### API

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/left?filter=&offset=&limit=` | элементы, кроме выбранных; `limit` ≤ 20 |
| `GET` | `/api/right?filter=&offset=&limit=` | выбранные в их порядке; `limit` ≤ 20 |
| `POST` | `/api/items` `{id}` | добавить элемент; дубликат → `409` |
| `POST` | `/api/select` `{id}` | перенести в правый список (в конец) |
| `POST` | `/api/deselect` `{id}` | вернуть в левый список |
| `POST` | `/api/reorder` `{id, anchorId, position}` | `position`: `before` \| `after` |
| `GET` | `/api/stats` | диагностика очереди (вне батчинга) |
| `GET` | `/healthz` | health-check (вне батчинга) |

Списки возвращают `{ items: [{id}], total, hasMore }`.

## 4. Frontend

* Две панели, у каждой своя прокрутка, свой фильтр и своя пагинация.
* Бесконечная прокрутка: `IntersectionObserver` на «маячке» в конце списка плюс добор порций,
  пока список короче контейнера.
* Фильтр с задержкой 300 мс; при смене фильтра окно сбрасывается и грузится первая порция.
* Выбор - клик по элементу слева; снятие - кнопка «×» справа.
* Drag & Drop - нативный HTML5: перетаскивание в верхнюю/нижнюю половину строки задаёт
  вставку «до/после», отдельная зона внизу переносит элемент в конец.
* Изменения применяются оптимистично, а при ошибке списки перечитываются с сервера.
* Значения фильтров не персистятся - после перезагрузки они пустые, а выбранные элементы
  и их порядок приходят с сервера.

Учтено, что бэкенд батчит запросы: кнопка добавления показывает состояние «Добавляем…»,
пока операция ждёт своего окна (до 10 секунд) - это ожидаемое поведение, а не зависание.

## 5. Развёртывание на бесплатном хостинге

Приложению нужен **долгоживущий процесс** с состоянием в памяти и таймерами, поэтому
serverless-площадки (Vercel / Netlify Functions / Cloudflare Workers) не подходят.

### Работающая версия

Приложение развёрнуто на Render: <https://million-list-1qn5.onrender.com/>

План бесплатный, поэтому после ~15 минут без трафика инстанс засыпает. Первый заход после
паузы занимает 30-60 секунд: браузер в это время может показать `ERR_EMPTY_RESPONSE`.
Порядок прогрева - открыть `/healthz`, дождаться `{"ok":true}`, затем открыть корень;
пока идут запросы, инстанс не спит.

### Вариант 1 - Render, план free

В репозитории лежит `render.yaml`, поэтому деплой сводится к трём шагам:

1. Запушить проект в GitHub / GitLab / Bitbucket.
2. В Render: **New → Blueprint**, выбрать репозиторий и применить `render.yaml`.
3. Render соберёт фронтенд и запустит сервер; публичный адрес появится в дашборде.

Что прописано в `render.yaml`:

| Параметр | Значение |
|---|---|
| Build Command | `npm install --prefix backend && npm install --prefix frontend --include=dev && npm run build --prefix frontend` |
| Start Command | `npm start --prefix backend` |
| Health Check Path | `/healthz` |
| Plan | `free` |

Те же значения можно ввести вручную при создании обычного **Web Service** (Runtime: Node),
если не хочется использовать Blueprint. Документация: [render.com/docs/free](https://render.com/docs/free).

### Вариант 2 - любой Docker-хостинг

В репозитории есть `Dockerfile` (многоступенчатая сборка: фронтенд → runtime с Express).
Образ слушает порт из `PORT` и отдаёт health-check `/healthz`.

```bash
docker build -t million-list .
docker run -p 4000:4000 million-list
```

Подойдёт любая площадка, принимающая Docker-образ: Koyeb, Fly.io, Railway и другие.
Если площадка работает по buildpack, а не по Docker, используется `Procfile` (`web: npm start`),
а команду сборки нужно задать вручную: `npm run setup && npm run build`.

### Важно про бесплатные тарифы и хранение в памяти

Бесплатные инстансы **засыпают при простое** (у Render - примерно через 15 минут) и просыпаются
при новом запросе (холодный старт - несколько секунд). Так как состояние по условию задачи хранится только
в оперативной памяти, после засыпания список выбранных обнуляется. Это согласуется с
формулировкой «хранение в оперативной памяти на протяжении времени работы приложения»,
но об этом стоит помнить при демонстрации. Если состояние нужно сохранять между
перезапусками, потребуется постоянно активный инстанс либо база данных.

Heroku не используется: бесплатный тариф там отменён в 2022 году.

### Если сборка или запуск на хостинге упали

* Проверь, что выполняются обе установки: `npm install --prefix backend` и
  `npm install --prefix frontend --include=dev`. Флаг `--include=dev` обязателен, если платформа
  выставляет `NODE_ENV=production`: без него не поставятся vite и typescript, и сборка упадёт.
* Start Command должен быть `npm start --prefix backend`; сервер слушает порт из переменной `PORT`.
* Health check должен смотреть на `/healthz`.
* Логи сборки и рантайма - в дашборде Render на вкладках Events и Logs.

## 6. Осознанные решения и ограничения

* **Базовый диапазон виртуальный.** Один миллион объектов в памяти не создаётся; память
  зависит только от числа выбранных и добавленных ID.
* **Фильтр кешируется по строке.** Кеш ограничен 20 записями; при смене фильтра старые
  вытесняются.
* **Пагинация по offset.** Для базового диапазона без фильтра страница ищется линейным
  проходом с пропуском выбранных. При типичной работе это доли миллисекунды; проход по
  миллиону элементов заметен только при экстремально глубокой прокрутке.
* **Порядок левого списка:** базовые ID по возрастанию, затем добавленные вручную.
* **Батчинг умышленно замедляет одиночные операции** (до 1 с и до 10 с). Так требует
  задание; окна настраиваются переменными окружения.
* **Стилистика Drag & Drop.** Перестановка при активном фильтре выполняется относительно
  видимого ориентира, поэтому после снятия фильтра элемент окажется рядом с ним.
* **Автотесты покрывают логику и HTTP API**; интерактивная проверка интерфейса в браузере
  в этой среде не выполнялась (нет браузерного инструментария) - UI проверен сборкой,
  раздачей статики и сквозными запросами к API.

## 7. Структура проекта

```
backend/
  src/constants.js   общие константы (BASE_MAX = 1 000 000, размер страницы)
  src/store.js       состояние в памяти, выбор, порядок, пагинация списков
  src/filter.js      подстрочный фильтр по виртуальному диапазону
  src/queue.js       очередь, дедупликация, батчинг
  src/routes.js      HTTP-маршруты API
  src/app.js         сборка Express-приложения
  src/index.js       запуск сервера
  scripts/           автотесты (логика и HTTP)
frontend/
  src/api.ts         обращения к API
  src/utils.ts       порядок ID и подстрочный фильтр (как на сервере)
  src/hooks/         бесконечная прокрутка и список с фильтрацией
  src/components/    левая и правая панели
  src/App.tsx        компоновка, оптимистичные обновления, уведомления
  src/styles.css     стили
render.yaml          blueprint бесплатного веб-сервиса Render
Dockerfile           универсальный образ для деплоя
Procfile             запуск для buildpack-площадок
```
